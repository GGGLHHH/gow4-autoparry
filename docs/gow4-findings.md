## 提示的输入条件判定：`0x87ac70`（自动 QTE 的 hook 点）

函数签名：`bool check(ctx* rcx, prompt* rdx, out* r8)`。所有 QTE 和互动提示都靠它判断「这次输入算不算满足条件」。

- `[prompt+0xe8]` u16 是动作 ID。值为 `0x3f` 或 `0x40` 时，函数直接返回 1。
- `[prompt+0xef]` u8 是输入类型，取值 1–13：
  - 1、2、9、10：分别调用 `0xf42b0`、`0x1f8550`、`0x4375b0`、`0x437370`，用来查询按键状态，推测分别是按下、按住等。
  - 5：按住要达到 `[prompt+0xf4]` 指定的时长（半精度浮点；值为 -1 时取全局配置 `+0x998`）。
  - 0xb、0xc、0xd：**连按**。条件是 `ctx[10]+0x4b4` 等于按键掩码，并且 `ctx[10]+0x4b0` 处的浮点数不超过全局阈值 `+0x978/0x97c/0x980`。如果 **重複按按鈕** ≠ 0，改用类型 5 的「按住时长」来判断。
- 按键掩码来自 `0xd85c30[动作ID-1]`；动作 ID 为 0x186、0x187 时另走一条路径。
- 条件满足时，尾调用 `0x87b770(ctx, prompt)`；不满足时返回 0。
- 全局 `+0x22E795B`（含义未知，也是辅助类设置）不为 0 时，只放行类型 3、6、9、10。
- 函数开头：`4C8BDC 56 4154 4155 4883EC60`，共 12 字节，没有 rip 相对寻址，可以直接搬进跳板。

### 弹反 / 格挡线索（第二场战斗后，2026-11-14）

- L1 的判定节点：类型 7 = 按住（举盾，满足会持续 2–3 秒），类型 1 = 按下那一下。每次按 L1 会同时判定 4–8 个节点（类型 1/3/4/7/8/9），是状态机里从不同状态出发的 L1 跳转。
- 节点对象（prompt）里没有名字：`+0x0` 指针、`+0xc0` 起是标志和输入参数（`+0xe8` 动作ID、`+0xef` 类型）、`+0x108` 指针。光看 `0x87ac70` 分不出哪个是格挡、哪个是弹反。
- 枚举 `eCMT_*`（值表在 `.data` `0x1120298`）：Invalid=0、**Block=1、Evade=2、Parry=3**、SonGrab_Success=4、SonGrab_Fail=5、SonFollowUp=6。推测是「玩家格挡 / 闪避 / 弹反成功」时发给阿特柔斯 AI 或脚本的战斗消息类型。
  找到写入 3 的代码，就能定位「弹反成功」的判定点。
- 投射物标志：`kFPayloadNotOnBlock`、`kFPayloadNotOnParry`、`kFDeflectParry`（标志值表在 `0x1126868` 一带）。
- 游戏数据里有 `luahook_perk_defense_onparry_*`（弹反成功时触发的护符 / 技能钩子）、`_parryattack_light/heavy`、`_parryprojectile`。

- 对象管理器 `M = *(GoW+0x123b5d8)`。两组区块数组：`M+0x10`、`M+0x1918`，各自 `+0x1900` 处是 u32 个数（上限 800）。

## 自动弹反 v4.4 定稿的机制（2026-11-14 实测 + 反编译）

- **弹反动作由动作状态机决定，不由命中结算决定**：只在结算里换弹反体（v2）结果和自然弹反一样，但不出动作。必须在命中时奎托斯正处于「刚按 L1」的弹反窗口。
- **做法**：hook 碰撞→命中入口 `0x8c9e30(a,b,c,d,e)`（`a+0x20` 攻击者生物，`b+0x20` 受击者生物），第一下先不进结算（原函数本身有直接 return 的分支）；同时在按键条件判定 `0x87ac70` 里把动作 ID 0x05（L1）类型 1/7 强制成立 450 ms。实测按下后约 6 ms（下一帧）防御组换上半径 10 的弹反体，同一刀的下一次碰撞放行 → 游戏自己的弹反。弹反成功的标志：约 120–145 ms 后奎托斯对攻击者有一次命中，命中标志 `0002000200001000`（盾震）。
- **可弹反角度是数据**：`0x724fe0` 用 `0x723b60` 算攻击者相对奎托斯的角度（0–360°，正前方 = 奎托斯矩阵 **-row2**，攻击者在 row0 一侧时取 360-角度），再查受击区域表 `防御组件+0x10e0`（键：防御组 `+0xf8`，为 0 用 `*(防御组件+0x10d0)+0x18`；值数组 `[0]`骨骼哈希、`[1..8]` 区域 `{哈希, ?, 起始角 +8, 结束角 +0xc}`，起始>结束表示跨 0°）。查到的区域哈希就是命中记录 `+0xd0`（格挡判定的 p6）。奎托斯默认表：
  - `011CBBEB9CE82EB8`：270°..90°（正前方左右各 90°）——弹反体 `+0x20` 只认这个
  - `000042500EBF0338`：90°..270°（后半圈）
- **后半圈**：即使强行让 p6=0 匹配上弹反体，状态机也只接「转身格挡」（防御组换成 `…15ADE8` 那组，第 6 个是全掩码保护体），不出弹反。后半圈要用闪避处理。
- **玩家自己按着 L1 时**：替他松开 34 ms 再按，碰撞只持续 40–80 ms，来不及进窗口，反而吞掉了格挡 → v4.4 改成不干预，照常格挡。
- **踩过的坑**：`0x8c9e30` 在 `0x8ca2e3` 读未初始化的 `[rbp+0x78]`（第一次写在 `0x8ca3e9`）。曾怀疑钩子栈残值导致 p6 错，实际 p6 异常是区域不同；调原函数前清 4 KB 栈的保护保留着。
- **闪避未解决**：只改条件判定结果（× 动作 ID 0x01 类型 1 和 9）不会触发闪避；手动闪避时防御组不变、成功的闪避根本没有碰撞事件。下一步考虑直接写手柄状态里的按键位/摇杆。

## 自动闪避 v5.8 定稿（2026-11-14 实测 + 反编译）

稳定版快照：`release/v5.8/`（DLL、注入器、ini），源码快照 `src/autoparry/autoparry_v5.8_stable.cpp.txt`。

- **奎托斯的手柄** = 全局对象 `GoW+0x2506320`（按键状态 `+0xe8` 就是条件判定读的那份）。
  - `0x140438770(手柄, 原始键号, 按压量0..255)`：游戏自己的单键置位，写 `+0x68[键]`、`+0x10` 原始掩码，按重映射表 `+0x318` 写 `+0x140[键]` 按压量和 `+0xe8` 掩码。重映射是恒等的；× = 键号 6 / 掩码 `0x40`。
  - 按键历史环：状态 `+0x48` 指针、`+0x50` 大小 16、`+0x52` 头、`+0x54` 尾；头 = `0xffff` 时（游戏暂停）所有按键条件都不成立。
  - 条件类型：1 = 本帧按下（当前有、历史最新一帧没有）；9 = N 帧内按下；10 = N 帧内松开（`0x437370`）。
  - 左摇杆：`+0x1c8` 原始 (x, y)，相对镜头，W = (0, 1)；`+0x1d0`/`+0x1d8`/`+0x1f0` 平滑副本，`+0x1e0` 角度（度，atan2(x, y)），`+0x1e4` 力度，`+0x1e8` 单位方向。输入上下文 `+0x410/414/418` 是换算后的世界方向，`+0x41c` 是力度（`0x14087b770` 拿它和角色朝向做点积、叉积，判断前后左右）。
- **闪避 = 方向 + ×**。光按 × 不闪。键盘玩家也一样，键盘最后落到同一个手柄对象上。
- **写入时机是关键**：
  - 只在每帧输入轮询 `0x14086b2c0` 之后写：游戏读按键之前会被重算覆盖，条件判定一次都没认到（v5.4、v5.6 失败）。
  - 在按键条件判定 `0x87ac70` 被调用时（奎托斯的上下文）写：`+0xe8`、`+0x10` 或上 `0x40`，`+0x68[6]`、`+0x140[6]` = 255，摇杆各副本 + 上下文 `+0x410` 世界方向，再加上轮询后那一次，就能闪（v5.7：朝闪避方向 1.5–2.2 m / 0.4 s）。
  - × 按住 200 ms，和手按的 150–200 ms 对齐。
- **镜头换算**：相机 `*(GoW+0x22a93d0)+0xaa0` 世界矩阵，行 0 是右，行 2 是后。摇杆 x = dot(世界方向, 右)，y = dot(世界方向, -后)。
- **什么时候闪**：背后半圈的刀、巨魔 `gotroll*` 的刀。巨魔的近战（命中标志高位 `0004`）在弹反窗口里格挡判定也能通过、输出也是 1，但奎托斯不进弹反成功状态（0/9），所以改成闪避。
- **吞刀按「同一刀」**：同一个攻击者的碰撞间隔 < 150 ms 算同一刀。闪过的那一刀整段吞掉，最长 2 s；巨魔下砸的冲击波能连着碰 1 秒多、追到 5 m 外。新的一刀离上次闪避至少隔 0.4 s。
- **追错过的路**：`0x1406b8e50` / `0x1406b8cb0` 会读奎托斯 `+0x4670`（匹配上的防御体），但它们属于 `attachment::tThrowable`（投掷物被挡后的反弹），不是近战反应。
- **限制**：现在是刀碰到奎托斯时才闪（先吞后闪），画面上是「被砍中的瞬间开始闪」。真正的提前闪需要读敌人出招的预警。

## 预判闪避 v6.8 定稿（2026-11-14 实测 + 静态数据）

### 招式系统（敌我通用，生物 `+0x3a70` = `ms::MoveSystemMutable`）
| 偏移 | 含义 |
|---|---|
| `+0x118` | 当前招式静态数据指针 |
| `+0x128` | 当前招式哈希（= 招式 `+0x40`） |
| `+0xd4` | 本招已进行时间（招式时间，按 `+0xe8` 速率走） |
| `+0xe4` | 整招时长（秒） |
| `+0xe8` | 播放速率 |

招式静态数据：`+0x20` 记录指针数组、`+0x28` 个数。记录头 = `u32 类型` + `f16 开始` + `f16 结束`（占整招比例）。
类型 `0x1d` 是定时动作：`+0x10` 动作类型哈希，`+0x18` 参数。`0x47895f0c39c33568` = 贴标签，参数是标签哈希

## 重新逆向一遍后的结论（2026-11-15，v6.18–v6.20）

### 奎托斯指针：用游戏自己的（v6.20）

- 脚本接口 `FindPlayer`（`0x8267b0`）读全局 `*(GoW+0x22e7d50)` = 玩家对象 `P`；`*(P+8)` = 奎托斯的生物；生物 `+8` = 游戏对象，对象 `+0x278` 最低位 = 有效。`PlayerIs`（`0x84d190`）同款取法。生物 `+0x3a58` 指回 `P`（`GetPlayer` `0x222030` 调它的虚函数 `[2]`，电脑控制的生物返回 0）。
- 运行时核对（pid 11316）：`P=…8218D0`，生物 `…7A9520`，对象名 `goheroa00`，对象 `+0x220` 指回同一个生物 —— 就是挨打的那个。

### 格挡判定 `0x79f0c0` 的完整条件

1. 先看生物 `+0x3978` 起的 3 个槽：某槽「`+0x638 == +0x634` 且 `*(槽+8)` 的 `+0x78` 非 0」→ 直接返回没挡住。
2. 逐个防御组调 `0x9140b0(攻击者, 受击者, 防御组, 防御组+0x80, &命中标志, &p5, &p6)`，返回匹配到的防御体；都没有 → 没挡住。
3. **弹反 = 匹配到的防御体 `+0x40` > 0，并且攻击者到受击者的距离 ≤ 这个值**。奎托斯的弹反体是 10 → 攻击者要在 10 m 内。
4. 近战结算 `0x8c72a0` 在判定成立后自己再匹配一遍，把防御体写进受击者 `+0x4670`（之前当成 32 位读错了，是 64 位指针）。

弹反体只在按下 L1 后的一小段时间里：日志里「按下后多少毫秒 / 匹配到哪种防御体」统计，0–140 ms 全是弹反体（半径 10），140–160 ms 两种都有，160 ms 以后全是普通格挡体（半径 0）。**弹反窗口 ≈ 按下后 155 ms**。

### 飞行物：游戏自己为什么从没判过弹反

提前按 L1 的那些火球，游戏原判定全是「挡住、不算弹反」，两个原因各占一部分：
- 匹配到弹反体的那些，发射者都在 12.8–19.8 m 外，超过 10 m；
- 发射者在 10 m 内的那几次（5.4 / 5.8 / 7.3 / 9.2 m），是按下后 156–176 ms 才打到，弹反体已经换成普通格挡体。

所以原版游戏里远处射来的火球只能挡、弹不回去；现在的「强制判成弹反」正好补这一条。只要打到时奎托斯举着盾（匹配到任意防御体）再强制成弹反，就会反弹；没举盾时强制（v6.14）不反弹。

- 飞行物发射者：`proj+0xf0` 是对象句柄（最低位 1 且 `& 0xfc000000000` 为 0）：id = `(h>>1)&0xffff`，下标 = `(h>>0x12)&0xfffff`，`(h>>0x11)&1` 选偏移 `0x20`/`8`；表在 `GoW+0x22a98c0..0x22a9ac0`（64 个指针，`*(int*)项 == id`）。阿特柔斯的箭发射者是 `goson00`，命中标志 `0002000004000000` / `0000000024000000` / `0000000104000000`。v6.19 按发射者排除后，一场里 20 多支箭全部没再触发按 L1。
- 反弹本身不在飞行物模块里：`0x814000–0x81c000` 没有任何指令测 `FDeflect*`（2/4/8/0x10）这几位；结束函数 `0x818020` 只调 `0x81aac0`（按 `FPayloadNotOn*` 决定要不要生成落点效果）；`0x81acc0` 是命中特效（事件 0x20e 弹反 / 0x20f 挡住 / 0x20d 普通）。反弹在下游（命中事件 `0x8c9300` 之后）决定，没追到。
- `0x6b8cb0`（`attachment::tThrowable`）：投掷武器状态 `+0x1438` 是 `0x10/0x20/0x400` 时，读受击者 `+0x4670` 的防御体 `+0x28`（1–4，对应 `kBRA*` 一类的「被挡反应」）决定武器弹开方式，参数在 `+0x30`。是敌人的投掷武器 / 我方斧子被盾挡的反应，不是飞行物反弹。

### 游戏怎么判「这一刀盾接不接得住」

格挡判定 `0x9140b0(攻击者, 受害者, 防御组[], n, &命中标志 u64, &p5 u32, &p6 u64)`，一个防御体 v 匹配的条件（全部成立）：

1. `命中标志 & *(u64*)(v+0x10) != 0`
2. `p5 & *(u32*)(v+0x18) != 0`
3. `*(v+0x20) == 0`，或等于 p6，或 p6 == 0（方位区哈希）
4. `*(v+8) == 0`，或攻击者 / 受害者为空，或条件对象 `0x7c33a0(受害者, 攻击者, 0)` 为真

生物自己的防御组查完，还会查全局表 `GoW+0x2d29000..0x2d29100`（16 项 × {GO 句柄, 指针}，防御体在 `指针+0x28`）里挂在受害者名下的最多 8 个。

### 弹反成功后敌人为什么会 / 不会被震开

`0x8c6cf0(命中上下文, 结果)` 给**攻击者**挑后续反应（`上下文+0x70` = 攻击者生物，`+0x90` = 攻击者当前招式）。结果结构的字节：`+0x11` 打死了 → 事件 `kEKill(0x1f)`；`+0x12` 打晕 → `kEStun(0x20)`；`+0x14` → `kEHealth(0x22)`；`+0x19` 被挡 → `kEBlockBreak(0x21)` / `kEBlocked(0x1e)`；`+0x1b` **被弹反**（就是格挡判定的第二个输出）→ 直接取

```
*( *(攻击者生物 + 0x4c30) + 0x448 )      // 生物定义.ParryReaction
```

拿不到（为 0）才退回普通的 `kEBlocked` 跳转。所以：

- `生物+0x4c30` = 生物定义（字段表结构号 `0x344`）。`+0x448 ParryReaction`（指针，被弹反时播的招式）、`+0x450 ParryMask`、`+0x458 BlockMask`（都是 `kHit*` 掩码）、`+0x460 RaySourceJoint`。
- 巨魔「格挡判定通过、输出 = 1，但奎托斯不进弹反成功、巨魔也不踉跄」最可能就是它的定义里 `ParryReaction` 为空 —— **待验证**（当时场上没有敌人，读不到）。
- 实读（只读，`tools/defmask.py`）：奎托斯 `ParryReaction=0`、`ParryMask=7FFF…`、`BlockMask=0`；阿特柔斯三个都是 0。
- **v6.21 实测（18:04–18:08 巴德尔战）**：`gobaldur00` 的定义三个字段全是 0，但他照样被弹反、被震开（6 次尝试 3 次震到，另 2 次游戏判成弹反、奎托斯进了弹反招式 `0AA263D8C05D360D` 只是没震到）。所以 **`ParryReaction` 为空不妨碍弹反**，它只是一个可选的覆盖项，为空就退回招式里普通的 `kEBlocked` 跳转；上面「巨魔是因为 ParryReaction 为空」的猜测**不成立**，巨魔的原因还得另找（要看它招式里有没有 `kEBlocked` 跳转）。
- 同一场新增两条档位数据，都符合掩码规则：`0000020100200040`（第 21 位）、`0000220100008040`（第 15 位）→ 判定返回 1 输出 1；红光拳 `0004020000080040`（第 19 位）3 次全部走闪避。
- `ParryMask` / `BlockMask` 在代码里没找到直接引用（按 `+0x4c30` 再 `+0x450/+0x458` 扫全代码段没有），含义还不确定。v6.21 起每种敌人第一次碰到奎托斯时在日志里记一行「敌人定义」，攒够几种敌人再对照。

## 招式预读：不等命中就知道这一招是什么（2026-11-15，v6.22）

用户的判断是对的：敌人一进招式，这一招会打出来的每一段攻击已经在招式的静态数据里，之前只是在命中那一刻才从碰撞上下文 `+0x80` 取。

### 数据在哪（exe 字段描述表给出了字段名，`tools/fieldsby.py`）

- **招式 Move（结构号 `0x3ca`）**：`+0x00 BranchList`、**`+0x10 CollisionList`**（指针数组 + `+0x18` 个数）、`+0x20 ActionList`（时间轴记录，个数 `+0x28`）、`+0x38 AnimName`、`+0x40 MoveName`（哈希）、`+0x50 PlaybackSpeed`、`+0x5a Duration`（f16，常是 -1 = 用动画时长）、`+0x5c Flags`。
- **攻击段 Collision（结构号 `0x12f`）= 碰撞上下文 `+0x80` 的「攻击定义」**：`+0x00 On` / `+0x02 Off`（f16，占整招比例）、`+0x04 HitPause`、`+0x06 BlockPause`、`+0x08 Damage`、`+0x0a Stun`、`+0x40 PartFlags`、**`+0x44 Flags`**（`kFUnblockable=4`、`kFOnlyHitAI=0x800`、`kFOnlyHitPlayer=0x1000`、`kFIgnoreHostile=0x8000`）、**`+0x48 HitFlags`**、`+0x78 HitJoint`、`+0x88 SphereOverrides`。
- **冲击波 Concussion（结构号 `0xc5`）**：`+0x08 DataType`、`+0x0a Flags`、`+0x10 PlayFX`、`+0x18 JointName`、**`+0x38 Collision`**（指向一个 `0x12f`）、`+0x48 HitFlags`、`+0x50 DurationList`。
- **招式怎么引用冲击波**：时间轴里的 `kTScript(0x1d)` 记录，`+0x10` 动作哈希 = `SCR_Concussion`，**`+0x18` 直接就是冲击波数据的指针**（`SCR_Concussion` 更新函数 `0x296690` 这么取）。记录自己的 `+4/+6`（f16）是放出冲击波的时间窗。
- **脚本动作哈希算法解开了**（注册代码 `0x296ae0`，和标签哈希同一个）：逐字符转大写，`h += c; h *= 0x401; h ^= h >> 6`，64 位、初值 0、无收尾，输入是类名全称。`SCR_Concussion = fd0a8735bc354673`、`SCR_AddMarker = 47895f0c39c33568`（就是之前叫「标签动作」的那个）、`SCR_UseHitModifier = 355ac50cf9d3a398`、`SCR_BroadcastReaction = 93488ab2bd209f57`、`SCR_CancelMove = 10d29779af452ead`、`SCR_SpawnProjectile = 9622f53d681d24a5`。282 个类的全表在 `docs/scr-action-hashes.txt`。之前见过的 `64690e541a03e30f`、`e52d5ed74860b645`、`af1e44c61242fc42` 不在 `SCR_*` 类名里，还没对上。

### 验证（都是只读）

- 奎托斯普攻 `7713EE8C404CE77E`：攻击段 1 个，`On 0.124 Off 0.155`、伤害 8、`HitFlags 0000400000000448`。
- 巴德尔近战 `6079648B55B3D727`（内存按命中标志反查，`tools/findcoll.py`）：段 0 `On 0.293 Off 1.000` 伤害 11 `Flags 0x1000` `HitFlags 0000220100008040`；段 1 `Flags 0x6800`（只打 AI）。日志里这一招接触在「本招 1.170 s / 标签到 1.250 s」→ 时长 1.25 s，窗口 = 0.366–1.25 s，接触落在窗口里；按「秒」解释则 1.17 s 在 0.293–1.0 之外 → **On/Off 是比例，要乘运行时时长**（招式系统 `+0xe4`）。
- 攻击段窗口很宽，真正接触取决于武器什么时候扫到人，所以**出伤时刻还是用 Attacking 标签结束来估**，攻击段只用来读属性。
- 冲击波链：内存里 1935 条 `SCR_Concussion` 记录，1934 条沿「记录 +0x18 → +0x38」读到的 Collision 数值合理；其中不可格挡 352 条、盾接不了 12 条、只打 AI 674 条。有 `HitFlags 0004000000080040`（和巴德尔红光拳同一档位）、记录窗口 0.6–1.0 的。

### v6.22 的做法（源码已改、已编到 `build\check\`）

- `ReadMoveAtk(招式)`：读 CollisionList，再递归 ActionList（容器记录 `kTContainer=1` 的子记录数组在 `+0x20/+0x28`）找 `SCR_Concussion`，得到这一招的全部攻击段。每个敌人每招只读一次。
- `NextThreat`：能打玩家（`Flags & 0x8800 == 0`）、还没结束的段里最早的一段。它「不可格挡 / 盾掩码接不了」→ 正面来的也提前闪；原来只有背后和巨魔才预判，非近战的一律不管。
- 出伤时刻：近战段按 Attacking 标签结束；冲击波按脚本记录开始 × 时长。
- 日志：`预读 <敌人> 招式 …：N 段攻击`（每招一次）、`⇒ 预判闪避 … 依据预读：…`、`预读核对 … 对上了 / ✗ 不在这一招预读的攻击段里`（命中时拿真实攻击定义去对）。

## 飞行物：高位 0004 不是「不可格挡」（2026-11-15，v6.23）

起因：用户说「被一个远程攻击打中了」。日志（v6.21，18:48–18:49）里 `gofanatic00` 的 4 发飞行物，命中标志 `0004000000008044`：

- 飞行物预判（`ProjPredict`）一条 `◇ 飞行物飞向奎托斯` 都没记 —— 它开头就因为「命中标志高 16 位 & 4」直接返回了，没提前按 L1；
- 格挡判定（调用者 `GoW+819146` / `GoW+8C7366`）返回 0，匹配防御体 = 0（当时根本没举盾）；
- 碰撞入口把它当「不可格挡（红光）」→ 碰到那一刻吞掉 + 按 ×。4 次都吞了，没有一次放行给游戏结算。

所以记录上没有一发真的结算了伤害，但飞行物是飞到身上才处理的（没弹回去，看着就是被打中再闪开）。

### 静态数据怎么说

内存里按命中标志反查攻击定义（Collision，飞行物数据结构 `0x134` 内嵌在 `+0x50`）：

| 飞行物 | Collision | 伤害 | Flags（+0x44） | 命中标志 | 飞行物标志（data+0x1a8） |
|---|---|---|---|---|---|
| gofanatic00 | `0x7ff355aebaf8` 等 3 份 | 10 | `0x1000`（kFOnlyHitPlayer） | `0004000000008044` | `0x41` |
| godraugr00 火球（一直能弹回去） | `0x7ff371e1da68` | 9 | `0x1000` | `0000402100008044` | `0x41` |

两者除了命中标志的高位不同，其余一样：没有 `kFUnblockable(4)`、没有 `kFIgnoreShield`，等级位都是第 15 位（在盾的掩码 `0x278000` 里）。按游戏自己的匹配规则（命中标志 & 防御体掩码 ≠ 0），盾接得住。

结论：**命中标志高 16 位的 `0004`（第 50 位）不是「不可格挡」**。它是 v6.11 从巴德尔红光拳（`0004020000080040`）猜出来的，但红光拳接不了的真正原因是等级位第 19 位不在盾掩码里（v6.21 的 `NoShield` 已经覆盖）；巨魔近战 `0004000400008000` 带这一位照样过格挡判定。带这一位的三种攻击（红光拳、巨魔下砸、这种飞行物）共同点是打中后是重受击，推测它是「重击 / 击倒档」，给受击方挑反应用（跳转记录 `+0xa8/+0xb0` 的命中标志条件）—— 推测，没验证。

|---|---|---|

### 机关和箱子的所属关系（游戏自己的父子层级）

对象 `GO+0x28`（`+0x140` 是同一个值）= **父对象指针**。实读三个诺恩宝箱：

| 机关 | 战利品的父链 | 机关的父链 |
|---|---|---|
| 铃铛（riv420） | `gochestpouchlegendary ← golootobject ← gochest_locked_parent ← gochest_runic_tier1_riv420_1 ← goriv420_cbt` | `gobelltargetfront ← goanimgroup ← gobellgeo ← gobelltarget_small_root ← goriv420bell_01 ← goriv420_cbt` |
| 转盘（riv475） | `… ← gochest_locked_parent ← gochest_locked_tier3_riv475_1 ← go____spinchest_setup____ ← goriv475_cbt` | `gospinner ← gospinner_02 ← go____spinchest_setup____` |
| 封印（riv925） | `… ← gochest_locked_parent ← … ← goriv925_cbt` | `gorunic#_break ← … ← goriv925_cbt` |

普通传说宝箱是 `gochestpouchlegendary ← golootobject ← gochest_legendary_parent ← gochest_legendary_scripted ← 区域组`，父链上没有 `gochest_locked_parent`。

所以：

- **诺恩宝箱的战利品** = 父链上有 `gochest_locked_parent`（或 `gochest_runic*`）。不再靠「离箱子 2 m 内」（开箱后战利品会挪到 1.8 m，差点出界），距离只留作兜底。
- **箱子所在的组** = 父链上最上面那个 `gochest_*` 的父对象（铃铛型是区域组 `goriv420_cbt`，转盘型是专门的 `go____spinchest_setup____`）。
- **机关属于哪个箱子** = 机关挂在那个组下面（同组多个箱子取最近）。箱子的战利品已拿（`+0x278 & 0x200000` 清零）→ 机关不再标。
- 层级对不上时：铃铛按距离兜底（120 m 内最近的诺恩宝箱），封印照旧只看自己的状态位，转盘直接不标（`gospinner` 这个名字太普通）。

转盘型的组里还有：`gobase_001`（带 `gocylinder` 和 `gorunegroup1..3` 的另一根柱子，离转盘柱约 5 m）、`gobase_002/003`（转盘的底座）、两个 `*_drainpoint`（`gobifrostdraincrystal`）。透视只标 `gospinner`，两节叠在一根柱子上（相隔 1.1 m）合成一个标签「符文转盘」。

没验证的：铃铛敲响 / 转盘对上 / 机关解开时对象上哪一位变化还没看过，所以「解开了但箱子还没开」那一会儿机关还会标着。有没有「箱子脚本直接引用机关」的更直接的指针没查成（扫内存时那片区域被游戏卸载了）。
